# 飞书项目推进员：团队安装与 Codex 使用说明

面向神来－圆周率团队成员。每个人在自己的电脑、自己的 Codex 项目窗口使用 `$feishu-project-runner`，从飞书群接收本人任务，执行后检查，再按授权报告成果。

**角色名：飞书项目推进员。技能调用名：`$feishu-project-runner`。** 角色名方便沟通，不会创建另一个机器人、账号或后台进程；实际能力来自已安装的 skill、本人飞书授权、项目配置及真实调度器。

阅读顺序：安装 → 核对本人身份和分工 → 手动完成一轮 → 验证 → 按需开启自动运行。Tinker 网页登录及其邮件服务不参与此流程。

## 一、准备什么

| 项目 | 成员需要准备的内容 |
| --- | --- |
| Codex | 能打开本人实际项目目录并执行本机命令的 Codex；网页云端任务不能直接使用这套本机 launchd |
| 安装环境 | Git、Node.js >=18；可选后台运行另需 macOS、Python 3 和支持 `codex queue` 的 Codex CLI |
| 飞书 | 本人账号能访问项目群；已配置、授权的官方 lark-cli，以及预期的报告机器人 |
| 项目目录 | 自己存放交付物、配置、任务台账和检查证据的工作目录 |
| 本人职责 | 从最新群分工核对；刚子和11各有职责，不能照抄另一人的授权范围 |

不要求成员手工寻找 open_id、会话ID或编写 plist；下面的接入指令让 Codex 核验并准备。缺少权限、工具或业务分工时，应说明具体缺项，不伪造配置。真实凭据、群历史和个人配置不提交到 GitHub。

## 二、安装：两种方法选一种

### 方法A：让 Codex 帮你安装

打开自己的 Codex，复制下面整段。此时技能尚未安装，所以先给普通安装指令：

```text
请为我安装飞书项目推进 skill，使用仓库
https://github.com/ikedamiho41-hue3333333333/tinker
的 feat/feishu-project-runner 分支。

先检查 Git、Node.js >=18 和 Codex 的技能目录。
若本机已有同名 feishu-project-runner（包括旧路径 ~/.codex/skills），
先比较版本、保留备份，选定一个安装位置，避免重复加载；不要动现有项目调度。
在独立下载目录取此分支，运行仓库 cli/bin/tinker.js 的 skills install，
参数为 --agent codex --only feishu-project-runner。
验证 SKILL.md、references、scripts、assets、agents 均已安装且引用有效。

只安装和核对文件，不登录 Tinker，不发送飞书消息，不启用定时任务。
依赖缺失时先查官方安装方法；需要账号授权或系统审批时保留原有门禁。
最后告诉我安装位置，以及怎样在自己的项目窗口看到这个 skill。
```

### 方法B：成员自己在终端安装

仅首次下载时，在一个没有同名 `tinker-feishu-runner` 目录的位置运行：

```sh
git clone --branch feat/feishu-project-runner --single-branch https://github.com/ikedamiho41-hue3333333333/tinker.git tinker-feishu-runner
cd tinker-feishu-runner
node cli/bin/tinker.js skills install --agent codex --only feishu-project-runner
```

结果应显示已安装 `feishu-project-runner`，位置为 `~/.agents/skills`。脚本会复制完整资源，更新同名技能前保留旧目录备份并输出路径。若旧路径已安装同名技能，先比较版本和安装位置，不直接制造两个同名入口。

当前安装说明使用集成分支；上游合并后可改用含该功能的正式版本。在旧版 Tinker CLI 上直接执行新参数不能证明已经安装此版本。以上安装命令本身不需要 `npm install`、Tinker 登录或飞书登录；读取真实飞书时仍需要自己的飞书授权。

安装后打开**本人实际项目目录**的 Codex 窗口，通过 `/skills` 核对 `$feishu-project-runner` 及路径。界面未更新时重新打开项目窗口，不把下载仓库默认当成项目工作目录。

## 三、首次接入：先核对，不执行任务

把下面整段发到实际项目工作窗口。将 `【我的飞书姓名】` 替换成自己的名字；其余内容可原样使用。不要把11的姓名或会话复制成自己的身份。

```text
使用 $feishu-project-runner。你是我的“飞书项目推进员”。

本人飞书姓名：【我的飞书姓名】。
项目：神来－圆周率。任务来源：飞书群“神来”。
工作目录：当前项目目录；请核对真实路径，不使用下载仓库或同事路径代替。

先按 skill 做只读接入检查：
1. 使用官方 lark-cli，核验登录用户就是本人，解析项目群的真实 chat_id。
2. 完整读取群历史、相关话题和关键分工附件，从最新确认核对我的职责、任务和授权。
3. 核对报告机器人。刚子默认使用饺子；其他成员核对本人可用且明确选择的机器人，
   未指定身份时沿用适用的当前配置与已有规则，无法确认则说明缺项，不擅自改成真人发信。
4. 根据包内模板准备本项目独立的 .feishu-project-runner/config.json，
   使用本人真实身份，不共用同事凭据、私有配置、会话ID或台账。
5. 首次接入未明确授权报告和调度时，保持二者关闭；已有配置则先核对，不覆盖有效授权。

本次仅生成本地配置和任务台账，不执行群任务、不发送消息、不开启自动调度。
向我集中展示：本人身份、群、项目路径、职责来源、本人任务清单、机器人、
建议的报告对象及各自下一动作、缺少的权限或必要决定。
不要展示密钥或令牌。
```

成员只需补充真实缺项、完成本人飞书授权或纠正分工。授权若由 Codex 发起，应使用实际缺少的最小权限，展示真实授权链接及二维码，成员完成后告知 Codex，由它完成后续核验。不要向 Codex 聊天窗口粘贴 appSecret/accessToken。身份或业务归属不能核实时，不进入执行步骤。

## 四、手动试跑：推进本人工作

接入结果正确后，复制下面指令。这里的“本人职责”必须已核对，不能仅凭角色名称推导。

```text
使用 $feishu-project-runner，以我的“飞书项目推进员”角色执行一轮。

按已核对的本项目配置和最新群分工，推进本人已授权范围内的任务。
先取得独占执行权、核验身份并完整回读群消息，核对是否有新指令或撤回。
继续既有未完成事项；同事的新交付满足依赖时恢复我的待办。
同轮持续处理可执行工作，完成子任务后继续下一项，不逐项等待我说“继续”。

按照实际验收要求检查交付物，保存版本、证据、未完成事项及下一动作。
只在实质成果已完成并检查后，按现有具体发送授权和门禁发报告；
尚无发送授权时先给我完整正文、目标群、发送身份和真实@对象的预览。
报告@我本人，并按最新分工添加需要接手、修订或确认的成员，写清各自下一动作。
不发配置、巡检、纯启动或未检查成果的群报告。

需要本人介入时集中提出具体决定和建议，未变化的已通知问题不重复问；
仅阻塞相关事项，继续其他已授权工作，保留真人签收与系统审批。
本轮收尾在当前窗口告诉我实际完成、检查结果、报告送达状态和阻塞。
```

完成试跑后，需要给后续实质成果报告明确授权时，成员可按自身真实意愿使用下句；若本地规则仍要求逐次发送确认，则保留该门禁：

```text
我授权你在当前已核对的本人任务范围内，实质成果完成并检查后，
按本项目配置用已核验的机器人向飞书群“神来”报告，@我本人及按分工需要行动的成员。
不发配置或巡检消息，不新增共享对象或敏感内容；保留现有发送确认和高风险审批要求。
```

## 五、怎样判定试跑成功

| 环节 | 需要看到的真实证据 |
| --- | --- |
| 读群 | 本人身份核验、完整分页、消息/附件来源；不能只说“已收到消息” |
| 识别任务 | 任务确实分配给本人，有输入版本、职责来源、范围与验收要求 |
| 执行 | 本人实际交付物及可访问版本；不能拿同事成果冒领 |
| 检查 | 按验收要求运行的检查、结果和证据；页面走查须操作真实页面 |
| 报告 | 有授权才发送；正文、机器人、群和@对象正确，发送后回读确认 |
| 保留进度 | 本项目台账记录准确，下一轮能继续未完成工作且不重复报告 |

没有本人可执行任务时，只能说明“接入/读群核验完成，等待真实任务”，不能为验证编造任务或发空报告。读群成功不代表上表所有环节通过；准备稿不等于人工验收。试用结果先在本人窗口汇报，不向群发送试用巡检消息。

## 六、开启全天每10分钟自动推进

手动试跑正常、本人确实需要自动运行时，在**同一个项目窗口**发下面指令：

```text
使用 $feishu-project-runner，为我的神来－圆周率项目配置自动推进。
我授权本机全天24小时、每10分钟检查飞书群“神来”，
继续本人已授权范围内的任务，并沿用已有成果报告授权及发送门禁。

先检查是否已有本人项目调度；有则核对并复用，不重复部署。
核对 macOS、Python 3、官方 lark-cli 和 codex queue 的实际可用性。
按 skill 包内 references/automation.md 部署本人独立配置与 launchd，
绑定我的既有项目会话，核验真实 thread_id/session_log，不使用同事会话或绕过审批参数。
保持完整任务台账在本项目目录，后台只保留调度状态及任务摘要。

启用后验证真实系统触发、本人身份、全量读群、目标会话实际收到指令；
有本人真实任务时验证执行和检查，不能把入队回执当成任务完成。
若尚未观察到真实自动触发，准确标为待验证，继续完成核验后再声明已运行。
不支持所需调度方式时明确说明，并保留手动调用，不制造后台运行的假象。
所有配置、巡检和安装核验只在当前窗口说明，不发群消息。
```

当前随包脚本只支持该项目的全天600秒模式，以及支持 queue 的 Codex 既有会话；其他项目、Windows/Linux 或指定时间窗口需要适配并验证。电脑需开机、登录、联网，授权和目标会话可用；休眠期间不运行。关闭执行窗口前先核对目标会话仍可接收，不假设会自动另建会话。完整技术步骤见 [调度说明](automation.md)。

## 七、日常可以直接复制的短指令

| 目的 | 发到本人项目窗口的指令 |
| --- | --- |
| 手动推进 | `使用 $feishu-project-runner，完整回读神来群，继续本人已授权的可执行任务，实际检查后按既有授权报告成果。` |
| 只看状态 | `使用 $feishu-project-runner，只读检查本人台账和真实调度记录，告诉我当前进度、阻塞及恢复条件，不执行任务或发送消息。` |
| 看群新任务 | `使用 $feishu-project-runner，核对最新群消息是否产生本人新任务、撤回或依赖恢复；更新本地台账，不发送巡检消息。` |
| 暂停 | `暂停本人神来项目自动推进，关闭本人调度业务派发并停止后续执行；保存进度，保留其他成员服务。` |
| 明确恢复 | `我明确允许恢复本人神来项目自动推进。使用 $feishu-project-runner，先核对最新群授权和暂停原因，恢复本人调度并验证真实运行；未获批准的业务决定仍保持待答。` |

## 八、常见问题

**需要角色名才能触发吗？** 不需要。写 `$feishu-project-runner` 更明确；“飞书项目推进员”只是方便团队记忆的名称。

**报告到底@谁？** 始终@配置中的本人。还需要谁接手、修订或确认，就按最新分工核验其真人身份后添加，并写明下一动作；不统一把所有成员都@刚子，也不@全体。刚子使用时@刚子，11使用时@11，角色由本人配置决定。

**为什么还会问我？** 常规实现按已有范围推进；真实缺凭据、业务签收、范围批准或发送/系统门禁时仍须本人处理。同项已问未变不重复催问，不阻塞无关工作。

**装好就会全天运行吗？** 不会。先完成本人接入与试跑，再授权并验证真实调度。只发一个提示词不能证明定时器存在。

**群里发了消息却没执行？** 在本人窗口用“只看状态”指令，检查最近真实触发、完整读取、会话忙碌/入队、暂停和具体错误。消息也可能不属于本人任务，或缺输入/批准；不能仅凭群消息已出现就判定故障。

**怎样更新版本？** 回到下载仓库，核对远程与分支后运行 `git pull --ff-only`，重新执行选装命令，再核对技能入口与备份。若有本地修改，先保留并比较，不强制覆盖。不要未经核对将正在运行的后台脚本和个人配置一并替换。

**飞书工具或权限缺失？** 让 Codex 按官方 [lark-cli 说明](https://github.com/larksuite/cli) 检查安装和应用配置。用户授权与机器人权限分开处理，只补实际缺项；机器人权限问题不能靠给用户反复登录解决。

更详细的配置字段见 [首次接入](onboarding.md)，项目阶段与报告对象见 [神来分工参考](shenlai.md)；这些参考都要与最新群确认核对。

项目目录/分支变化后须重新核对实际调度绑定，并按[分支调度与连续执行](continuation.md)验证完整链路；不要保留manual_branch_only却宣称自动运行。
